# コーディング・プリンシプル

## 適用しない場合

次のときは読み飛ばしてよい。

- 1ファイルで完結する単発の編集（typo、設定値、定数の変更）
- コードを書かない調査・説明タスク

判断に迷ったら適用する側に倒す。

## 1. 着手前に、完了をどう判定するかを決める

実装を始める前に「何が満たされたら完了か」を、機械的に成功・失敗が判定できる形で決める。
test / typecheck / lint / build / schema validation / smoke test のいずれかに落ちるのが望ましい。

- README、package.json、pyproject.toml、Makefile、justfile、CI設定を先に読み、
  プロジェクト標準の検証コマンドを特定する。自分で新しいコマンドを考えるのはその後。
- コードを変更したら、対応する検証コマンドを実際に実行する。
- 失敗したら出力を読み、原因を推定し、修正し、再実行する。推測で「直ったはず」と書かない。
- 機械的に検証できない項目が残ったら、未検証であることを報告に明記する。
  ここを省略すると、動作確認していないものを確認済みとして渡すことになる。

## 2. 変更は、検証ループが回る単位に分ける

一度に扱うのは、検証可能なひとつの目的だけにする。
失敗したときに原因を局所化できる粒度を保つのが目的であって、
作業を途中で止めてよいという意味ではない。依頼されたスコープは最後までやり切る。

- 大きな変更は、各段階で検証が通る小さなステップに分ける。
- 振る舞いを変える変更と、振る舞いを変えない整理（リネーム、フォーマット、移動）を混ぜない。
  混ざると、検証が落ちたときにどちらが原因か切り分けられなくなる。
- コミットも同じ粒度で分ける。ただし「まとめてコミットして」と言われたらそれに従う。

## 3. 意図をコードの近くに残す

コードを読めば分かる処理内容は書かない。コードからは復元できない情報だけを残す。

残す価値があるのは、仕様、制約、前提条件、設計判断、トレードオフ、回避策、
そして「なぜ以前の実装ではなくこうしたか」。

- コメントの量と文体は周囲のコードに合わせる。コメントの少ないファイルで
  自分の変更箇所だけ解説を足すと、そこが浮いて逆に読みにくくなる。
- 編集時は、既存のコメント・docstring・テスト名から元の意図を読み取ってから変更する。
- コメントとコードが矛盾していたら、どちらが正しいかを確認し、
  コード・コメント・テストをまとめて更新する。放置すると次に読む人が誤情報を信じる。

## 4. 重要な制約は、人が見張らなくても検出できる形にする

自然言語の説明だけに頼らず、型、スキーマ、テスト、assertion、validation、lint rule で表現する。
レビューで気づくことに依存した制約は、いずれ破られる。

優先度が高いのは、入力値・出力値・エラー条件・境界条件・セキュリティ要件・
レイヤー間の依存方向・禁止 API。

新しい仕組みを足す前に、既存のもの（型定義、既存のテスト、設定済みの lint ルール）で
表現できないかを先に確認する。ガードレールを増やしすぎると、それ自体が保守対象になる。

## 5. テストは決定的にする

時刻、乱数、ネットワーク、外部 API、共有状態、実行順序に依存するテストは、
mock / fake / fixture / local emulator / container で依存を制御する。

- ローカルと CI で結果が変わらないようにする。
- 決定的にできない場合は、その理由をテストの近くに書く。
- flaky test を見つけたら放置しない。原因を特定するか、少なくとも報告する。
- 明示的な指示がない限り、本番環境・実データ・外部課金サービスには接続しない。

## 6. バグ修正と機能追加はテストから書く

テスト基盤があるプロジェクトでは `red -> green -> refactor` を実践する。
先に失敗するテストを書くことで、修正が本当に効いたことを確認できる。
テストが最初から通ってしまったら、再現条件を取り違えている。

テストフレームワークが無い場合や、テストが書けない種類の変更（設定ファイル、
ドキュメント、UI の見た目）ではこの限りではない。無理に導入するより、
原則1の機械的な検証手段を別の形で用意する。

## 完了時の報告

検証を実行したときは、次を簡潔に添える。実行していない項目は書かない。

- 実行した検証コマンドとその結果
- 未検証事項
- 既知の制約または残課題
