# プログラミングタスクに取り組む際の「コーディング・プリンシプル」

ユーザーからコーディングを依頼されたとき、この原則に従ってください。

# P1. コードと意図をコロケーションし、各コードファイルを「動作するドキュメント」として捉えてください。

- コードと、そのコードを理解・変更・検証するためのコメントを、近くに配置してください。
- 命名（ファイル名、変数名、関数名など）の際は、簡潔で短く、わかりやすい命名をしてください。
- 仕様、制約、前提条件、設計判断、トレードオフ、回避策については、意図をコメントとして積極的に残してください。
- コードを読めば明らかな処理内容だけを、コメントで繰り返さないでください。
- 編集時も同様です。既存のコメント、docstring、テスト名、近接するドキュメントから意図を読み取り、それを踏まえてコードを編集してください。
- 動作を変更するなら、以前の動作からなぜ変更するのか、意図をコメント、docstring、テスト、または近接するドキュメントに残してください。
- コメントとコードが矛盾する場合は、どちらが正しいかを確認し、コード・コメント・テストを一緒に更新してください。

# P2. 完了条件を「機械的に検証可能な契約」として定義してください。

- 実装前に、何が満たされれば完了なのかを明確にしてください。
- 完了条件は、 test / typecheck / lint / build / schema validation / smoke test など、機械的に成功・失敗を判定できる形にしてください。
- 既存の README、package.json、pyproject.toml、Makefile、justfile、CI設定などを確認し、プロジェクト標準の検証コマンドに従ってください。
- コードを変更したら、対応する検証コマンドを実行してください。
- 失敗した場合は、出力を読み、原因を推定し、修正し、再度検証してください。
- 検証できない項目がある場合は、未検証事項として明示してください。

# P3. 仕様・制約・不変条件をコード上のガードレールとして表現してください。

- 重要な仕様は、自然言語の説明だけでなく、型、スキーマ、テスト、assertion、validation、lint rule などで表現してください。
- 特に、入力値、出力値、エラー条件、境界条件、セキュリティ要件、レイヤー間の依存方向、禁止 API は、自動検出できる形にしてください。
- 暗黙の前提に依存しないでください。
- 人間なら文脈で理解できる制約も、AIが検証できる明示的なルールに変換してください。
- 新しいガードレールを追加する場合は、既存の仕組みで表現できないかを先に確認してください。

# P4. 変更は小さく、検証ループを回せる単位に分割してください。

- 一度の変更では、検証可能なひとつの目的だけを扱ってください。
- 大きな変更が必要な場合は、テストが通る小さなステップに分割してください。
- 各ステップで、変更、検証、修正、再検証のループを回してください。
- 振る舞いを変える変更と、振る舞いを変えない整理を混ぜないでください。
- 失敗したときに原因を局所化できる粒度を保ってください。
- 検証に失敗した場合は、直前の変更との差分を確認し、原因候補を小さく切り分けてください。

# P5. 実行環境・依存関係・副作用を明示し、再現可能にしてください。

- 実行に必要なコマンド、環境変数、依存サービス、テストデータ、前提条件を明示してください。
- テストは決定的にしてください。できない場合は理由を明示してください。
- 時刻、乱数、ネットワーク、外部 API、共有状態、実行順序に依存する場合は、その依存を明示し、mock / fake / fixture / local emulator / container などで制御してください。
- ローカルと CI で結果が変わらないようにしてください。
- flaky test を放置しないでください。
- 明示的な指示がない限り、本番環境、実データ、外部課金サービスには接続しないでください。

# その他実務的な内容

## 共通事項

- バグ修正や仕様追加では、特別な理由がない限り、テスト駆動開発の`red -> green -> refactor`のプラクティスを実践してください。
- 既存プロジェクトに package manager / runtime / lockfile / CI 設定がある場合は、既存方針を優先してください。

## 作業完了時の報告

作業完了時には、以下を簡潔に報告してください。

- 変更内容
- 実行した検証コマンド
- 検証結果
- 未検証事項
- 既知の制約または残課

## JavaScript/TypeScript 開発

- 新規 JavaScript/TypeScript プロジェクトでは、特別な理由がない限り `npm` の代わりに `bun` を使用してください。
- Linter/Formatterには`Biome`を使用してください。

## Python 開発

- 新規 Python プロジェクトでは、特別な理由がない限り `uv` を使用してください。
